# Agent Canvas

An auto-saved infinite canvas for live Pi Coding Agents. Each node contains a real, interactive Pi terminal; a directed connection represents **delegated work**, not automatic message passing. Agents can explicitly send messages to a running Pi node via the local API.

## Quick start

Requires Node.js 22.13+ (built-in SQLite), npm and an authenticated `pi` on your PATH.

```sh
npm install
npm run dev
```

Open **http://127.0.0.1:5173**. Enter an existing working directory's absolute path, or choose one from the saved Pi session folders dropdown, then either launch a **new Pi session** and type directly in its terminal, or select **Resume · pi -r** to pick an existing session inside the terminal. Canvas nodes and Pi conversations can be restored after server restart (see below). Newly created agents (New or Resume) are brought into view, selected, and focused so you can type immediately; reopening a stopped node also focuses its terminal. Initial page load and reconnect do not steal focus. Click inside any terminal to switch to it. Use the □ button in an agent's header to expand it to fill the browser window without entering browser fullscreen; click the return icon to go back to the whiteboard without changing its saved size or restarting Pi. Use the bell button in the top bar to opt into browser system notifications when an agent finishes a turn; the browser will ask for permission. Notifications are suppressed while its terminal is focused, and clicking an alert brings the agent into view. The bell can also turn notifications off. Keep the Canvas tab open for alerts (no background service worker). Stop ends its process but leaves the node and its output. A stopped node has a Remove button to delete it and its connections from this canvas (not Pi's saved session).

Use the single mouse/touchpad icon button beneath the bottom-left zoom controls to switch modes (the icon shows the current mode): **Mouse** uses right-drag to pan and the wheel to zoom; **Touchpad** uses two-finger scroll to pan and pinch to zoom. Drag nodes by their headers, resize selected nodes, and connect right-to-left handles to record delegation. Click a connection's label to edit its display text; the underlying relationship remains a delegation.

Use **＋ Note** to add a yellow sticky note. Notes display only their body text, with no title. Drag only the paper's top edge to move it, resize the note when selected, and edit its text directly (saved when the editor loses focus). Text scales with the canvas while staying at least 14 screen pixels for readability. Hover over the note to reveal **×** in the top-right corner and delete it (also available with keyboard focus or on touch devices). Notes are independent of agents and are saved with the Canvas.

## Card box (MVP)

Use **＋ Card** to create a separate Markdown card on the Canvas; sticky notes are unchanged. Cards have no title. The front renders Markdown; **Edit** opens the source editor; valid content and tags auto-save about 500 ms after typing stops. **Done** returns to reading without discarding the draft. A small status shows Saving / Saved / Not saved, with Retry on write failures. **Metadata ↷** flips to the immutable ID, editable comma-separated tags and **Links** (other card IDs, separated by commas or whitespace). Links auto-save with content/tags; metadata does not count toward the 400-unit content limit. Flip back with **Content ↶**. Drag the card header and resize selected cards. Canvas card content, metadata and editor text use a 13px base font that scales with the Canvas, with an 11-screen-pixel minimum when zoomed out. Sticky notes retain their 14-screen-pixel minimum. In Agent Canvas, **×** removes only its Canvas placement; **Delete permanently…** requires confirmation and removes the card from the library too.

**Card box** switches to a separate cards-only whiteboard (plus one fixed Pi terminal). **Agent Canvas** switches back. All library cards appear, including those not placed in Agent Canvas. Initial cards are arranged in a grid; new cards are added to free grid slots without moving existing cards. Drag/resize cards to organize them; Card box and Agent Canvas layouts are saved independently in the same JSON. Both views edit the same Markdown/tags/Links. Card box has no removal × because every card appears. Cards not already on Agent Canvas show a **＋** header icon to add them there without leaving Card box; the icon disappears once placed and reappears if removed from Agent Canvas. Permanent deletion removes the card from both views. No query/filter API is added yet.

Use **Start Card box agent** once to create its New session, working in `~/Documents/agent-canvas/` (the card database directory when overridden). This agent is unique, has no delegation handles, and cannot be removed or replaced by another launch. Stop retains it; Resume reopens its conversation. Switching views does not stop or remount terminals. Mode preference is remembered across reload; each view's viewport is retained while switching within the page. Restart restores previously running conversations using the existing exact-session/fallback rules, with no task replay. Card box agent instructions forbid directly editing SQLite/Canvas data files; this is guidance, not filesystem isolation. Links are automatically bidirectional: adding A → B adds B → A, and removing either end removes both, in one SQLite transaction. Links are shown as IDs; no clickable navigation, search or hierarchical tags yet. Up to 100 unique link IDs per card are allowed, including reverse links; a change that would exceed either card's limit is rejected without saving either side. New targets must exist, and self-links are rejected. Deleting a target retains its ID in referring cards as a historical reference; remove it manually if desired.

### Image and audio attachments

Each card supports at most **one image and one audio file**, shared by both Canvas modes. Drag files onto a particular card to upload; dropping onto empty Canvas does nothing. There is no file-picker button, external URL registration, clipboard paste or recording in this version. A single drop may contain one file of each kind; duplicate kinds/unsupported files are rejected before uploading.

The front displays **audio → image → Markdown text**, including while editing text. Images display in full without cropping; click to open a larger preview (×, Escape or background click closes it). Audio offers play/pause, a seek bar and time; it never autoplays. One shared player continues across mode switches, and playing another card pauses the previous audio. Unlinking/replacing the currently playing file or deleting its card stops it.

Supported images: **JPEG, PNG, WebP, GIF**, maximum **10 MB** each. Audio: **MP3, M4A, WAV, OGG**, maximum **50 MB** each. Limits use 1024-based MB. Uploads validate actual file signatures, not browser MIME labels; browser codec support still determines playback. Back-face metadata lists original names and sizes, with Remove controls. Replacing an existing file requires confirmation; stale concurrent replacements return a conflict rather than overwriting a newer attachment. Attachment saves are independent of Markdown drafts and the 400-unit limit.

Files are copied (originals untouched) into `images/` and `audios/` alongside the card database, normally `~/Documents/agent-canvas/`. UUID filenames avoid collisions; original names are stored in SQLite. **Accepted files and their metadata are retained** after unlinking, replacement or permanent card deletion, for a future manual audit. No audit/automatic cleanup is included now. Failed/uncommitted uploads are cleaned up. Two-file drops upload each file separately; a later failure does not undo an earlier successful upload.

Content is limited to **400 text units**: CJK graphemes count individually and non-CJK words count using Unicode word segmentation. Mixed content is added together. Markdown syntax, link destinations, whitespace and punctuation do not count; code text counts. Images embedded in Markdown and raw HTML are rejected; image/audio attachments use independent fields. UI and API share the same validator; over-limit drafts stay editable but are not saved, even after Done; the last valid stored content is preserved. Unsaved drafts exist only in the current page and are lost on reload. Existing cards above 400 units remain readable and deletable without truncation; further saves require shortening the content to the new limit. There is also a 20,000-character Markdown source limit. Tags: up to 30 unique strings, at most 60 characters each, no commas/newlines.

Cards live independently in SQLite at `~/Documents/agent-canvas/cards.sqlite` (override with `AGENT_CANVAS_CARDS_FILE`). IDs use the server's local date and a daily non-reused sequence, e.g. `2026-10-03-0001`. SQLite transactions protect ID allocation. SQLite automatically migrates older libraries to schema 4: schema 2 adds the Links column, and schema 3 fills missing reverse links between existing cards in one transaction, retaining references to deleted cards. Schema 4 adds attachment-file metadata and one image/audio reference per card, without changing existing content or links. If backfilling would exceed a card's 100-link limit, migration fails without partially adding reverse links. Older code supporting only SQLite schemas 2/3 cannot open the migrated database; use separate test data when checking out older commits. On startup an online SQLite backup is saved to `cards.sqlite.bak`; do not copy a running WAL database as a single file. For a manual full backup, stop the server and copy the Canvas JSON, SQLite file, and the complete images/ and audios/ directories (including unlinked files). These two stores are not a single atomic transaction: a card may survive a failed Canvas save, and missing-card placements are discarded on restore.

Canvas saves now use schema version 2 and read existing version-1 files. **Older branches cannot load version-2 saves**; when testing this branch separately, use a separate state file and card database. Reset clears Agent Canvas placements but preserves the card library, Card box layouts and its agent.

On the first default-path startup, if the new data directory is absent or empty, a stopped legacy `~/.agent-canvas/` is copied into `~/Documents/agent-canvas/` automatically. Original files remain as a recovery copy. Migration refuses to copy data owned by a live server, includes any remaining SQLite WAL/SHM files, and excludes process locks. Existing new-directory data is never overwritten or merged. Setting either storage-path environment override disables automatic migration. After migrating, the Documents directory is authoritative; the legacy copy is no longer updated.

## Auto-save, restore and reset

Both workspace layouts are auto-saved to `~/Documents/agent-canvas/canvas.json` (override with `AGENT_CANVAS_STATE_FILE`). Metadata changes are saved after 250 ms of inactivity with atomic replacement and a `.bak` previous-save backup. Normal shutdown flushes immediately. The file contains node metadata, notes, edges, layout, session identities and recent terminal output; treat it as private. Unsubmitted terminal input, active tools and browser viewport are not saved. Pointer mode and the notification opt-in are remembered locally by the browser. Agent turn state is live only and is not saved.

On restart, previously running nodes automatically reopen their exact Pi conversation with **no prompt sent**. Missing or invalid sessions fall back to `pi -r`; a nonzero process exit before Pi reports a loaded session also falls back once. Missing workdirs leave a stopped node with an error. Previously stopped nodes stay stopped; use **▶** to reopen their conversation. User-installed Pi extensions still run normally on startup.

**Reset Canvas** in Agent Canvas asks for confirmation, stops only its Pi processes, and clears its nodes/notes/edges/placements. Card box agent and layouts are unaffected. It does **not** delete cards in the card box, Pi sessions or project files. Save failures appear in the browser. Corrupt/unsupported save files prevent server startup instead of being overwritten; inspect the original and `.bak` before manually recovering. A process lock prevents multiple servers from opening the same save file; stale locks from exited processes are recovered automatically.
