# Agent Canvas API

Canvas launches you with `AGENT_CANVAS_URL` (the local server) and `AGENT_CANVAS_ID` (your node ID). Use your bash tool with `curl` to interact with the server. Before making Canvas API changes, read the **current, complete guide** from the running server:

```sh
curl -fsS "$AGENT_CANVAS_URL/api/docs"
```

This guide is the source of truth for endpoints, request shapes, and safety boundaries. For example, `curl -fsS "$AGENT_CANVAS_URL/api/state"` reads agents, edges, sticky notes, card-box cards and placements. If canvas_read is available, use it for paginated shared-memory Canvas summaries without HTTP; it is not the full state, a human-gesture lease check or proof of task success. Follow nextOffset; memory errors are explicit and never perform HTTP fallback. Keep HTTP for the complete guide, other control/content mutations, authoritative geometry checks, output and full source. Prefer canvas_set_progress when available for your own progress note through the separate process-scoped Pi-to-Scratch SHM telemetry channel. Queued is not applied/saved; never resend uncertain outcomes or switch to HTTP on failure. Session/activity reporting is automatic; do not invoke internal callbacks. Temporary telemetry heartbeat expiry pauses writes; the same epoch can recover automatically with freshly sampled session/activity, not replayed progress or model wakes. Closed/replaced channels remain fenced. Never enable/restart shared-memory services or relaunch other agents automatically. Status queries omit terminal output: use GET /api/agents for metadata, GET /api/agents/:id for one agent, and GET /api/agents/:id/output for its bounded recent raw ANSI tail when needed. Use canvas_subscribe/canvas_unsubscribe for future Agent lifecycle/progress notifications when available, not a blocking wait. Default delivery is UI-only; conversation delivery is explicit, and followUp requires once:true and cannot target yourself. Avoid automatic wake cycles. Subscriptions are session-scoped, with explicit gap/stale errors; already-idle does not emit a new event, and idle is not task success. HTTP wait has been removed (404); there is no canvas_wait tool or automatic HTTP-only fallback. Never guess agent IDs; get them from state. If the server cannot be reached, do not guess or improvise API calls.

Only create delegation edges for work actually delegated; edges do not send messages. Prefer canvas_send_message when available to contact a running agent through your SHM outbox and Scratch routing, not terminal paste. Default nextTurn never wakes; followUp/wake must be explicit, with finite rate/process budgets. Use IDs from canvas_read; target process generation is pinned. Queued is not accepted; delivered only proves the receiver invoked Pi's API, not model processing or completion. canvas_message_status reads the last-known receipt without waiting; never run a model polling loop or automatically resend unknown outcomes. Never automatically reply/wake in a cycle. Messaging addresses the Pi process, not a session: reload/new/resume/fork retains queues, pending messages and receipt history, pauses handoff while no context is bound, and rebinds to the current Pi context. Do not relaunch agents for session changes. The legacy HTTP/TTY messages endpoint remains a separately chosen interface, never an automatic fallback. See docs/agent-messaging.md for the full contract. You may specify or adjust Agent Canvas positions/sizes for any Card, Note or Agent without extra confirmation; first read current geometry and follow the guide's non-overlap and human-interaction checks. Card Box positions, sizes and viewports remain human-only. Never spoof the browser's human-layout marker or manipulate gesture leases to bypass checks. Layout permission does not authorize content or lifecycle changes. Only update your own progress note, and do not stop, remove, resume or rename another agent, change a user's notes, or reset the canvas unless asked. Card-box cards are separate from sticky notes; fetch the guide for content limits, tags, and library-versus-placement lifecycle. Only create, modify or delete the user's cards when asked. This localhost API has no authentication; these rules are guidance, not an authorization boundary.
