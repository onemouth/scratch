# SHM agent-to-agent messaging

When available, use `canvas_send_message({agentId,text,delivery:"followUp",wake:true})`. Explicit followUp/wake:true is recommended so an idle recipient can start a model turn; reserve nextTurn/wake:false for intentionally passive context. Scratch routes your dedicated SHM outbox to the target process mailbox; native semaphores notify receivers. Program defaults remain nextTurn/wake:false and do not wake. Follow-ups retain 3/minute limits per sender and recipient, without a process-lifetime cap; all messages retain the 30/minute sender limit and bounded queues. The tool returns queued with a message ID; `canvas_message_status({messageId})` reads later receipts without waiting. Accepted means Scratch enqueued the pinned target generation; delivered only means the receiver invoked Pi's custom-message API, not read/answered/completed. Do not automatically resend uncertain outcomes or create reply/wake loops. Maximum text is 8000 UTF-8 bytes. No HTTP fallback, persistence or restart replay. Messaging is process-scoped: reload/new/resume/fork retains channels, pending messages and receipts, then rebinds handoff to the current Pi context. No process relaunch is needed for a session change.

## Targeting and bounded work

Get IDs from `canvas_read` or `canvas_agents`, never names or guesses. To require a particular process, query `canvas_agents({agentId})` and pass its `processGeneration` as `generation`; without it the tool pins the current advertised generation. Optional `ttlMs` defaults to 60000 (range 1–600000); maximum text is 8000 UTF-8 bytes. A receipt is last-known evidence, not a blocking wait; unknown is not safe to resend.

For delegated conversations, specify bounded rounds/work and an explicit completion/failure report. Verify actual returned content before advancing; report validation failure to the coordinator rather than silently leaving a peer waiting. This does not authorize automatic replies, retries or wake loops.

## Pending inbox (read-only browser view)

Each Agent header, including the Card box dock, opens a read-only inbox popover with sender, waiting time and full literal text. It shows only unresolved messages, not a receipt history. Pi API handoff does not remove a message: the process must observe its exact peer envelope in the model context and outgoing payload, followed by response content or a successful response end. Request failures/abort before response do not count. This is inclusion evidence, not task completion or an acknowledgment from the model.

Live Agent state includes an `inbox` summary `{state,count,revision,generation,reason?,previousUnconfirmed?}`. `count:null` means unavailable, never zero. `GET /api/agents/:id/inbox` returns this summary plus `messages:[{messageId,sourceId,sourceName,text,receivedAt,state}]`; item state is pending or uncertain. Reads never wake, mark consumed, send or replay anything; writes return 405. This browser content read does not add a SHM tool. Process end is unavailable; a new generation has fresh rows and an unresolved-previous-process warning when needed. Nothing is persisted or replayed across server restart. Capacity limits are 64 rows per recipient / 1024 total; exhaustion rejects new sends with MESSAGE_INBOX_FULL rather than evicting pending rows.
