# Architecture

Agent Canvas is one local Node.js server and a React browser client. The server owns the in-memory canvas and the Pi processes; the browser draws the canvas and acts as a terminal emulator. A single Canvas is auto-saved on disk and restored on restart; Pi conversations remain in Pi's own session files.

```text
Browser ── HTTP operations / SSE state / WebSocket terminal ── Scratch
Pi ────── SHM summaries, subscriptions, queries ──────────────┤
Pi ────── SHM telemetry and routed peer messages ─────────────┤
Pi ────── HTTP state, lifecycle/layout/content operations ────┘
                                                           ├─ Canvas maps / JSON
                                                           ├─ card library / SQLite
                                                           └─ node-pty → Pi TUI
```

## Ownership and data flow

- `server/index.js` is the composition root: Canvas maps, persistence, state publication and startup/shutdown. `server/canvas-operations.js` handles validated domain operations for cards/notes/views/layout/delegation; it takes operation inputs and returns status/value without HTTP objects. `server/agent-runtime.js` owns PTYs, process generations, session identity, activity and telemetry application. `server/http-routes.js` handles origin policy, body parsing, HTTP errors, media/static delivery and SSE. `server/terminal-transport.js` owns browser WebSocket subscriptions/I/O. `server/session-workdirs.js` scans session headers. An agent record retains its capped raw output tail; terminal bytes stream independently of metadata snapshots.
- `src/main.jsx` uses React Flow for pan, zoom, nodes, resize and connections. Layout changes are sent back to the server with `PATCH /api/agents/:id`. Mouse mode uses right-drag for pan and wheel for zoom; touchpad mode uses scroll for pan and pinch for zoom. The workdir dropdown reads only the `cwd` header of saved Pi session JSONL files via `GET /api/session-workdirs`; users can still type any valid directory. These are browser interaction choices, not Agent API concepts.
- An agent runs `pi` in interactive mode inside a `node-pty` process. **New** mode starts in the requested workdir, optionally with an initial task supplied through the API; the human UI launches it without a task so the user can type in the terminal. Pi saves its session normally. **Resume** mode runs `pi -r` there, opening Pi's own saved-session picker in the terminal without an initial task. Both receive `AGENT_CANVAS_URL` / `AGENT_CANVAS_ID`, a short appended system prompt pointing to the `agent-canvas` skill, and that skill via Pi's explicit `--skill` flag. The skill tells agents to fetch the current full API guide from the server when using Canvas. Child agents spawned via the API receive the same integration; stopped nodes receive it when explicitly resumed.
- `@xterm/xterm` renders PTY output and sends keystrokes to `/api/terminal/:id`; it uses a consistent 12px CSS font on all display densities, leaving high-DPI rendering to the browser. `@xterm/addon-fit` reports terminal column/row changes. Connecting to an existing node replays the server's recent raw output before subscribing to live output.
- `docs/agent-api.md` is the source for the in-app **API Guide** and the full reference linked from `skills/agent-canvas/SKILL.md`. `GET /api/docs` serves it as Markdown and replaces the URL in examples with the backend address or, when the browser requests it, its explicitly allowed Vite or public HTTPS origin. The guide can be copied into another agent.

## Shared-memory projection and subscriptions

`server/canvas-memory.js` publishes an allowlisted, bounded, ephemeral JSON projection through `native/canvas-shm` (POSIX shm_open + mmap, not an ordinary mapped file). Scratch is the sole writer. npm dev/start/test hooks compile the required addon. Metadata publication is coalesced; a separate one-second heartbeat tracks liveness. `server/pi-canvas-memory.js` provides paginated `canvas_read`; `shared/canvas-memory.js` validates the protocol and bounds model-facing pages. Opaque native handles return copied Buffers, not writable mapped JS memory. Each server has a unique name/epoch; bounded reads, heartbeat checks and graceful unlink prevent following stale/replacement generations. See [setup and protocol](shared-memory.md).

`server/canvas-notify.js` handles session-scoped subscriptions over a 256-record ordered SHM journal. Runtime transitions publish immediately. Private named semaphores and dedicated receiver threads (not libuv workers) notify Pi; UI-only delivery is default, and conversation/follow-up delivery is explicit. Subscriptions report gaps and transport errors rather than infer completion. See [notifications](canvas-notifications.md).

## Explicit SHM peer messaging

server/canvas-messages.js owns routing and per-run queues; server/canvas-message-client.js owns Pi-side publication, receipts and handoffs. native/canvas-shm/queue.cc implements claimed SPSC queues over real POSIX shared memory with atomic commit and non-overwriting backpressure. Four queues separate payloads from acks/receipts, with reserved terminal receipt credits. Each process uses independent messaging wake channels, not canvas_subscribe's semaphore. server/pi-canvas-messages.js registers canvas_send_message/canvas_message_status and uses Pi custom messages, never terminal input. Sender identity comes from the channel; target generations are pinned. Default nextTurn never wakes; follow-ups have explicit finite budgets. No persistence, replay, automatic resend or exactly-once claim. server/pi-message-process.js owns a process-scoped transport broker that survives extension-runtime replacement. Session shutdown detaches the old Pi API/context, pausing inbound handoffs; session_start rebinds the current API/context and drains queued work. Queues, receipt history and budgets survive reload/new/resume/fork. Pi retains native handles until process quit/cleanup. Temporary snapshot failures pause/recover on the original epoch; fatal failures fence operations without reconnecting. Scratch owns counterpart cleanup on process exit/server shutdown and unsafe routing failures. See [messaging contract and limitations](agent-messaging.md).

## Pending inbox

`shared/canvas-inbox.js` observes exact process-owned peer IDs/content in the current context and provider payload, then confirms inclusion only on a real response delta or successful assistant response end. `server/agent-inbox.js` owns a bounded ephemeral projection; `server/canvas-messages.js` applies channel-inferred, sequenced facts through the private ack queue. Ordinary delivered receipts still describe only API handoff. Session/runtime detachment marks handed-off unresolved rows uncertain; process close is unavailable and replacement never replays old rows.

Live browser snapshots add only inbox counts/revisions/availability; an open `src/agent-inbox.jsx` popover reads details via GET /api/agents/:id/inbox. This projection is not in Canvas JSON, public SHM summaries or precise metadata queries. Rendering is literal text through a viewport-clamped portal, independent of terminal DOM and Canvas scale. Reading has no delivery/consumption side effects. See [inbox contract](agent-inbox.md).

## Pi → Scratch telemetry

`server/canvas-telemetry.js` provisions independent reports/receipts queues and semaphores; `server/canvas-telemetry-client.js` publishes bounded activity/session/progress reports and collects application receipts. `server/pi-telemetry-process.js` keeps transport ownership, sequence and receipt history on the Pi process across extension-runtime replacements, rebinding only the current context. The tracker uses only this channel and registers `canvas_set_progress` for its own note. Scratch infers identity from the channel and validates current process generation before application; only Scratch updates Canvas/persistence. Activity transitions publish notification journal entries immediately. Session paths stay out of the public awareness snapshot. Receipts distinguish queued/applied/rejected/unknown; applied is not a disk-flush guarantee. Session/activity/progress use only telemetry. SHM failures never fall back to HTTP. See [telemetry protocol and lifecycle](agent-telemetry.md).

## Queries and output

`server/canvas-queries.js` owns dedicated per-process SHM request/response queues for precise runtime metadata and freshly sampled layout/busy. `server/canvas-query-client.js` and `server/pi-canvas-queries.js` provide `canvas_agents` / `canvas_layout` with byte-bounded pages, response credits, cancellation/deadlines, generation fencing and process-scoped ownership. Native queues support 1/16/64 KiB slots; query responses use 64 KiB slots. Full metadata travels only to the requester, not the public summary/event journal. See [query contract](agent-queries.md).

`GET /api/state` returns Canvas state without Agent terminal output. `GET /api/agents/:id/output` reads the recent 80,000-character raw ANSI tail for running or stopped agents; it is not a transcript or file-read API. Browser SSE includes state/output replay; WebSocket streams terminal I/O. Collection/state responses omit Interactive source; a single-card HTTP read supplies it.

Synchronous runtime change notifications publish SHM events, including process exit before restore fallback. Future-event subscriptions return immediately and deliver in the background.

## Default data directory

CLI defaults to `~/Documents/agent-canvas/` for both JSON and SQLite. `server/storage-paths.js` performs a one-time copy from a stopped legacy `~/.agent-canvas/` when the destination is absent/empty and no storage overrides are set. Legacy locks prevent copying a live database; the copy retains WAL/SHM and backups, omits locks, then atomically renames the staging directory. Originals remain untouched as recovery copies. Existing destination data is not merged.

## Card box storage

`server/card-store.js` owns a separate SQLite card library (schema version via `PRAGMA user_version`). Built-in `node:sqlite` requires Node 22.13+. WAL, FULL synchronous commits and transactions protect card writes and daily non-reused ID allocation. An online `backup()` creates a startup `.bak` snapshot. The SQLite file has its own exclusive process lock. A corrupt or unsupported library fails startup.

Live SSE snapshots include library `cards`, Agent Canvas `cardPlacements` and independent `cardBox.placements`. Canvas JSON schema 4 stores agents, notes, edges, Agent Canvas placements, Card box views and the Unfiled layout cache. Supported schemas 1–3 migrate on startup, preserving layout. Views store names, saved/temporary state, memberships, geometry and viewport, with one shared activeViewId. The fixed Unfiled view derives visible membership from cards absent from all ordinary views; its cache preserves layout while assigned cards are hidden. Temporary views persist for recovery but are not saved dropdown entries.

SQLite schema 8 owns Markdown/Interactive content, tags, bidirectional card links, timestamps, ordinary-attachment metadata and Interactive source/revision/private assets. Create/update synchronizes reverse links and timestamps in one transaction, including ID allocation on creation. New targets must exist and cannot reference self; exceeding either card's 100-link limit rolls back the whole operation. Deleted targets can remain as historical IDs in referring cards. Supported older libraries migrate transactionally; unsupported/corrupt data fails startup.

Agent Canvas reset/removal clears its placements, not the library or Card box workspace. Permanent card deletion removes placements and memberships in every view. Ordinary attachment files/metadata are retained after unlink/deletion; private Interactive assets are deleted through the card API. Missing-card placements are pruned on restore. SQLite and JSON are not a cross-store atomic transaction.

## Vault secrets and capabilities

`server/vault-crypto.js` implements password-derived wrapping and authenticated per-entry encryption; `server/card-store.js` schema 8 stores one Vault configuration and encrypted entries independently of library card records. Vault is managed from the top-right panel, with no card type or placement. `server/vault.js` owns unlocked key memory, ephemeral process capabilities, bounded approval requests and per-key generation grants. Agent retrieval resolves an exact key name and pins its entry identity; rename/delete cancel requests/revoke grants, and a recreated name cannot inherit authorization. `server/vault-http.js` exclusively handles protected human controls and process retrieval; generic card operations cannot mutate Vault data. Runtime launch/exit owns process credential creation/revocation. Startup is locked; reload/session changes do not recreate credentials. `src/vault.jsx` owns human connection, explicit secret editing and approval UI without persisted plaintext drafts. See [Vault lifecycle and threat model](vault.md).

## Card rendering and views

`src/cards.jsx` provides front/back Markdown and interactive cards in both workspaces. Interactive cards store agent-authored HTML/CSS/JavaScript in SQLite schema 8, render through an opaque-origin `sandbox="allow-scripts"` iframe with a restrictive CSP, and expose only exact CSP-listed URLs for validated card-private assets imported from the fixed local media folders. `src/jsxgraph-bundle.js` lazily imports the pinned JSXGraph distribution/CSS/MIT license as text; the document builder injects it before card JavaScript only when activated. It executes only inside the sandbox; network access, dynamic evaluation and WebAssembly are blocked. The Library never mounts their runtime; leaving visibility or changing source/assets destroys runtime state.

`src/main.jsx` keeps one React Flow instance with off-workspace nodes invisible (not unmounted), preserving terminal DOM, WebSocket and draft continuity. Only current-view Card box nodes are mounted; their in-page dirty drafts are cached by card/workspace, and pending valid writes finish in order on departure. Other workspace nodes remain mounted. The shared Card box agent is rendered outside React Flow in a fixed collapsible right sidebar, kept mounted even when hidden or off-workspace. Its stored coordinates are not used by the dock. Browser-local sidebar visibility is remembered, and notification/launch focus opens the dock. The canvas reserves dock width while open; the dock is excluded from fit/overview. The sidebar supports maximize/return and lifecycle controls. Visible canvas nodes alone drive fit/overview. Agent Canvas viewport is cached in-page; each Card box view's viewport is server-persisted. Mode preference survives reload.

`server/card-box-layout.js` assigns free slots only to view additions, preserving existing placements. `server/card-views.js` validates/migrates view state, maintains the fixed dynamic Unfiled view, protects temporary departure with an explicit save/discard and expected active ID, and keeps one shared current view. A monotonic snapshot revision and per-process epoch prevent older HTTP responses/SSE from reverting newer view state, while letting authoritative reconnects accept a new backend's recovered state. Layout/viewport gestures are scoped to their starting view and cannot write into a different view after a shared switch. `src/card-views.jsx` renders view controls and a paginated searchable responsive library sidebar. `src/card-view-explore.js` selects exact Unicode-normalized tag matches or the complete undirected component of recursively linked cards; metadata clicks create auto-fitted temporary views through the same guarded departure flow. Search uses Unicode-normalized OR substring matching over content/tags/ID; it is not fuzzy/semantic search. The full library metadata travels in SSE snapshots, but interactive source is fetched only when its visible card runtime mounts and inactive view cards are not mounted.

Card box contains only current-view cards and at most one fixed `workspace: 'card-box'` agent, stored with the normal lifecycle/session records. Its launch endpoint sets workdir to the database directory, with explicit instructions not to edit data files directly. All Canvas-launched Pi processes use regular TUI mode so browser xterm scrollback owns transcript scrolling. No delegation handles/edges or agent-removal action are supported there. `shared/card-content.js` parses Markdown into an AST, rejects images/raw HTML and counts CJK graphemes plus Unicode-segmented non-CJK words, up to 400 units. UI and server share this validator.

## Agent Canvas layout operations

`server/canvas-layout.js` reads only Agent Canvas agent/note/card-placement rectangles, checks finite bounds and strict AABB overlap (no gap; touching allowed), and tracks ephemeral multi-owner human gesture leases. Existing create/PATCH routes validate explicit ordinary API geometry before mutating records, creating a library card, or spawning a PTY. Creation without explicit geometry uses default placement. Rejections return structured 409 collision/busy details. canvas_layout exposes paginated, freshly sampled geometry and busy state through SHM; observations do not reserve a future write. Card Box is excluded. Explicit API-positioned launches get a live-only focus-suppression hint; normal layout updates never recenter the viewport.

The browser sends `X-Canvas-Layout: human` on its UI writes (an intent marker, not authentication) and uses `src/layout-interaction.js` for start/renew/end leases during Agent Canvas native drag/resize. A 3-second heartbeat renews a 10-second lease; release follows the final geometry write, with requests serialized to avoid delayed renewals resurrecting leases. Multi-tab owners coexist; disconnected tabs expire naturally. Human overlap remains allowed. Agents must not spoof the marker or lease endpoints; the API has no authentication boundary. `docs/agent-canvas-layout.md` defines this cooperative contract. Card Box geometry and viewport writes are view-scoped and human-only.

## Card media storage and playback

`server/card-media-store.js` streams raw uploads into exclusive 0600 staging files in `images/` or `audios/` (card database directory). It enforces 10/50 MB byte limits, uses patched `file-type` signature detection and canonical MIME/extension mappings, flushes file data, renames to a UUID filename and flushes the directory before committing SQLite association/file metadata. Failed uploads and concurrency/shutdown conflicts remove only uncommitted files; accepted files are never automatically removed. Original names are metadata, not filesystem paths. Per-slot compare-and-swap is checked before streaming and again inside the SQLite transaction, so concurrent replacements cannot overwrite a newly confirmed association. Attachment writes do not validate or overwrite Markdown drafts.

SQLite records and filesystem bytes cannot be one atomic transaction: a crash before DB commit can leave an unregistered/orphan file for a later audit, but associations are committed only after durable file creation. Startup backup covers database metadata, **not file bytes**; a complete backup must include both media directories. Metadata references missing files remain intact; serving returns 404 for missing files, symlinks or byte-size mismatches. File serving permits only validated registered UUID filenames (no arbitrary paths), refuses symlinks, uses canonical MIME/nosniff, HEAD/ETag and single-range 206/416 responses.

`src/card-media.jsx` implements card-target drag/drop, confirmed replacements, image previews and back-face unlink controls. Unsupported/duplicate kinds are rejected before upload; an image+audio drop consists of two independent requests. Upload errors preserve old associations and text drafts. `src/card-audio.js` owns one lazy browser Audio element; `useSyncExternalStore` keeps controls for both Canvas copies synchronized. Playback begins only on button click, continues across mode switches, and stops when its file is no longer referenced by any card. Recording, external URL attachments, Agent uploads, audit and automatic orphan cleanup are unsupported.

## Relationships and lifecycle

An edge `source → target` means the source **delegated work** to the target. Creating a child with `parentId` adds that edge; `POST /api/edges` can record delegation between existing agents. The edge's display `label` is editable via `PATCH /api/edges/:id`, while its `type` remains `delegates`. An edge is not a message channel and does not orchestrate execution. Explicit peer messaging uses SHM and Pi custom-message handoffs, not PTY pastes; API handoff is not proof of model processing. Messaging never creates edges.

An agent is `running` while its Pi process exists and `stopped` after exit or Stop. A finished Pi task leaves the interactive process available for follow-up prompts. Stopping a process keeps the node, its last output and all relationships until a human removes it or resets the Canvas. Only a fully stopped Agent Canvas node can be removed; the fixed Card box agent stays available for Resume and cannot be removed; removal deletes its in-memory node, terminal replay and incident edges, but never Pi's saved session files. Pi saves sessions independently. The server restores Canvas nodes and relationships and reopens previously running agents' conversations, without replaying their initial task or any terminal input.

## Persistence and session identity

`server/canvas-store.js` validates versioned snapshots and writes them through a flushed temporary file followed by atomic rename; the previous valid save becomes `.bak`. Metadata updates debounce for 250 ms. Graceful shutdown flushes running/stopped intent before terminating processes, so shutdown exits do not overwrite the restore decision. Output is captured in the next metadata save or shutdown flush, not on every streamed byte. Invalid saves fail startup without being overwritten. Save errors are exposed in state and the UI. The default CLI file is `~/Documents/agent-canvas/canvas.json`; `AGENT_CANVAS_STATE_FILE` overrides it. Test instances use `stateFile: null` unless explicitly testing persistence.

`server/pi-session-tracker.js` is passed via Pi's explicit `--extension` option. Its `session_start` hook reports the exact session file and ID on initial startup, resume, new session, fork, and reload. The same extension reports `working` on `agent_start` and `idle` on `agent_settled`, and initializes activity on session start. Activity reports have per-run increasing sequence numbers, are never saved, and do not trigger a completion alert on initial load or SSE reconnect. The browser offers opt-in system notifications only on a live `working → idle` transition, using the agent name as the title and a Unicode-safe, 120-character plain-text preview of the last assistant message as the body. The transient preview travels with the idle activity report and is never persisted. Alerts are suppressed for the currently focused agent. It needs an open tab and browser notification permission; it does not depend on Herdr. Reports use only process-scoped SHM telemetry, with channel-inferred identity/generation validation and monotonically increasing sequences across report kinds; old reports cannot overwrite newer state. These are cooperative checks, not an authentication boundary. The extension never sends messages or starts turns. The API binds before Pi launches, so the SHM report consumer is ready.

Restore validates the saved session file and identity, then launches `pi --session <path>` with no task arguments. Missing/invalid sessions use `pi -r`. A nonzero exit before the tracker reports readiness falls back to the picker once; later failures do not cause automatic relaunch loops. Missing workdirs retain a stopped node with a warning. Previously stopped nodes remain stopped and can be explicitly resumed in place. Third-party Pi extensions still run normally and may have their own startup behavior.

Agent Canvas reset requires confirmation, stops its agents (with bounded SIGKILL escalation), closes their terminal sockets and clears its nodes, notes, edges and placements. The Card box agent, views and library are preserved. Saved Pi sessions and project files are untouched. A PID-based exclusive lock prevents multiple servers from using the same save file; a lock left by a dead process is reclaimed at startup. Card box viewports and temporary view metadata are persisted; Agent Canvas viewport and unsubmitted terminal/card-editor input are not persisted across page reload. Pointer mode and notification opt-in live in browser localStorage; turn activity is ephemeral.

## Boundaries

The HTTP server always binds to `127.0.0.1`. By default it accepts only existing localhost browser origins (or absent Origin for local CLI clients). Optional `AGENT_CANVAS_PUBLIC_ORIGIN` adds exactly one validated HTTPS origin to the same HTTP/WS allowlist; validation occurs before opening storage. This does not authenticate requests, grant per-user privileges, or trust forwarded Host/Origin headers. Canvas-launched Pi agents keep their loopback URLs even when browsers use HTTPS.

Optional Tailscale Serve terminates TLS and proxies HTTPS/SSE/media and WSS to loopback Vite on fixed port 5173; Vite serves development modules/HMR and forwards /api (including terminal WS) to the loopback backend. Tailnet policies—not the Origin allowlist—control who can reach it. Permitted tailnet clients have the same terminal/file capabilities as local clients. `scripts/tailscale-setup.js` inspects connectivity/DNS/Serve state, is read-only by default, and requires `--apply` to configure a tailnet-only root HTTPS proxy to Vite (dev mode only). Vite permits the explicitly configured HTTPS hostname, uses strict port 5173, and detects ws/wss HMR URLs automatically; backend PORT overrides also update Vite's API target. No build/start step or production-target option is part of this setup. It leaves exactly matching configuration intact, refuses conflicts/unknown schema/Funnel, rechecks before applying and verifies afterwards. It never resets Serve, starts/stops Canvas, edits Canvas files, or changes access policies. Check/apply is not atomic against independent daemon changes, so do not configure Serve concurrently; post-apply verification detects conflicts but does not reset other people's configuration.

There is no authentication or isolation from other local processes. An agent with shell access can call the API, so the guide asks it to modify only its own note and to record relationships only for real delegation. This is guidance, not an authorization boundary. Never use Funnel or expose the backend to the public internet/LAN.

Terminal replay is limited to the last 80,000 raw characters per node; truncating an ANSI stream may make the replay after refresh visually incomplete. Browser xterm.js may not support all native terminal features (for example Kitty keyboard protocol, images or external-editor integration). Node resizing and the semantic API are intentionally separate.
